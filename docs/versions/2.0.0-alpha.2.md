# 2.0.0-alpha.2: procesos, señales e inspección

Estado: implementación Lua funcional en validación; el nuevo requisito de [core C independiente y binding oficial](../architecture/c-first.md) sigue pendiente. Alpha.2 todavía depende de cerrar [alpha.1](2.0.0-alpha.1.md) y sus checks aplicables en GitHub; Windows se valida en alpha.6 y no bloquea esta entrega; no se ha creado un tag ni una release. La API descrita es de Malvado, no una afirmación de compatibilidad completa con BennuGD.

## Nueva puerta de cierre

La API y tests de esta página describen el runner Lua actual. Para cerrar alpha.2 hay que mover el scheduler y procesos al core C sin dependencia Lua, exponer API C usable por juegos, conectar el binding Lua al mismo scheduler y verificar las rutas C, Lua y mixta. La interfaz de diagnóstico actual en `runtime.h` no es una API de juego C. El plan de migración y criterios concretos están en [arquitectura C](../architecture/c-first.md).

## Primer corte de API C

`include/malvado/malvado.h` expone un contexto opaco independiente, con creación/destrucción y reloj lógico de avance explícito. `MALVADO_BUILD_LUA=OFF` y `MALVADO_BUILD_RAYLIB=OFF` permiten compilar y probar este núcleo sin descargar Lua ni raylib. El [ejemplo C de reloj](../../examples/c/clock/README.md) también puede compilarse contra los archivos instalados.

Este corte **no implementa aún procesos C ni conecta el runner Lua al contexto nuevo**: ambos siguen en `src/runner/runtime.c`. La separación real del scheduler y la paridad C/Lua son los siguientes pasos, y siguen siendo requisitos de cierre de alpha.2. La API actual es experimental y no ofrece todavía garantía de ABI estable.

## API Lua

- `mv.process(fn)` crea un tipo; cada constructor devuelve un ID entero positivo único durante la ejecución. `mv.find(constructor)` devuelve una tabla nueva con los IDs vivos de ese tipo en orden de creación; incluye procesos dormidos y excluye los terminados o marcados para morir.
- `mv.signal(id, signal)` y `mv.signal_tree(id, signal)` aceptan `"sleep"`, `"freeze"`, `"wakeup"` y `"kill"`. La versión árbol afecta al proceso y a los descendientes vivos en ese momento; los hijos posteriores no heredan la señal. Un proceso marcado para morir no puede reactivarse. Las señales inválidas o IDs inexistentes generan error sin modificar el árbol.
- `mv.kill(id)` y `mv.kill_tree(id)` son atajos para terminar un proceso o su árbol. Una coroutine que se mata a sí misma continúa hasta ceder o retornar; la limpieza se realiza en un punto seguro. La señal aplicada a otro proceso lo afecta en ese tick si aún no se ha ejecutado.
- `mv.status(id)` devuelve `"running"`, `"sleeping"`, `"frozen"` o `nil` si no existe o ha sido marcado para morir. Los procesos suspendidos siguen existiendo y mantienen abierto el runtime.
- `mv.set_priority(id, value)` y `mv.get_priority(id)` usan enteros, con valor inicial 0. Los valores mayores se ejecutan primero y los empates siguen orden de creación. El orden se fija al empezar el tick; los cambios durante el tick se aplican en el siguiente. IDs inválidos generan error. `self.priority` no cambia la prioridad del scheduler.
- `mv.send(id, value)` y `self:recv()` implementan FIFO no bloqueante: `nil` significa cola vacía y no puede enviarse; los valores son referencias Lua compartidas. La cola admite 1.024 mensajes pendientes y produce error cuando se llena. Las referencias se liberan al terminar el proceso.
- `self.parent` contiene el ID del proceso creador o `nil`. Los hijos comienzan en el siguiente tick. La tabla `self` aún es modificable, pero el árbol interno conserva la relación creada por el scheduler. Si muere el padre, sus hijos vivos pasan a ser raíces del árbol interno y `self.parent` conserva el ID original.
- `mv.snapshot()` devuelve una copia con `tick` y una lista `processes`, con `id`, `parent`, `type`, `status`, `priority`, `messages`, `draw_commands` y `visible`. Es una fotografía del momento de llamada, incluso si se llama durante un tick; no contiene payloads ni ejecuta getters de usuario. Modificarla no altera el scheduler.

## Dibujo y estados

Las órdenes de `draw_text` pertenecen al proceso que las creó. Se reemplazan cuando ese proceso vuelve a ejecutarse y se conservan entre presentaciones. `freeze` mantiene visible el último dibujo, `sleep` lo oculta y `wakeup` lo vuelve a activar; `kill` lo elimina al terminar el proceso. Los textos persistentes creados con `write` tienen vida independiente y deben eliminarse explícitamente. El render de sprites y sus colisiones pertenecen a alpha.3 y no se consideran verificados aquí.

## Interfaz C para herramientas

`src/runner/runtime.h` expone un hook de diagnóstico llamado entre ticks, una copia de `MalvadoProcessInfo` en un buffer del consumidor, señales y control de pausa/avance de un tick (`malvado_debug_*`). La instantánea informa del total aunque la capacidad sea menor; los valores son copias y `status` es una cadena estática. Las llamadas son síncronas y deben ejecutarse en el hilo del runner; no hay acceso concurrente ni servidor de red. Un hook opcional de fotograma se ejecuta antes de presentar la imagen y se usa para la prueba gráfica. En pausa, la presentación puede continuar; `step` avanza un tick lógico, no una línea Lua.

Esta interfaz permite iniciar un futuro inspector, pero no implementa todavía el protocolo IPC ni la GUI. El orden del scheduler se ha separado en `src/core/schedule.c`; el ciclo de vida de procesos y el binding siguen dentro de `runtime.c`; separar la API C opaca y el backend permanece en alpha.1. No se afirma que la API actual sea definitiva para terceros.

## Verificación

CTest incluye trazas deterministas de prioridad, creación, árboles, señales, FIFO, colas repetidas, liberación por GC de mensajes pendientes, cleanup y errores con traceback. `debug_host` comprueba instantáneas, comandos, pausa y un paso; `inspection` comprueba búsqueda, copias y estados. El ejemplo de [inspección](../../examples/inspection/README.md) se ejecuta en CI. Con `-DMALVADO_VISUAL_TESTS=ON`, `visual_sleep_freeze` abre una ventana y comprueba píxeles para freeze/sleep/wakeup; requiere un display o pantalla virtual.

En macOS se han ejecutado pruebas headless, sanitizers y prueba gráfica; en Linux ARM64 se han ejecutado 23 pruebas, incluida la gráfica, en un contenedor con Xvfb y render por software. También se ha ejecutado el analizador estático de Clang sobre el C propio en macOS. El workflow incluye builds de macOS/Linux, sanitizers y prueba gráfica Linux; todavía debe ejecutarse en GitHub. Android y Windows se validan en alpha.6. El código de Lua y raylib se descarga en el build y el runtime contiene Lua compilado.

Los IDs son monotónicos y no se reutilizan. Los slots terminados se compactan tras cada tick; la capacidad conserva el máximo simultáneo alcanzado. La búsqueda es lineal y cada tick reserva y ordena una instantánea de ejecución; medir antes de optimizar. No se ha acreditado ausencia de fugas en todos los sistemas: los sanitizers cubren las pruebas ejecutadas, no todos los casos posibles.
