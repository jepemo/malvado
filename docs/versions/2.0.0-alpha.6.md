# 2.0.0-alpha.6: API inventory and assets

Status: in progress. Depends on [alpha.3](2.0.0-alpha.3.md) and the API contracts.

## Scope and planning gate

This version selects the 2.0 API inventory and delivers scroll, regions, collision, one FPG variant, and one Aseprite subset. It does not deliver every API family; the remaining selected families belong to alpha.8. Graphics modes 7–9 and GUI work remain outside 2.0.

The remaining API names are not decided. The initial FPG variant is selected in [FPG 8-bit](../specs/fpg-8.md). The initial Aseprite subset and its acceptance evidence are selected in the [asset decision](../specs/assets.md#alpha6-aseprite-acceptance-decision). The inventory and format decisions below must identify their inputs, exclusions, and acceptance tests. Split each selected capability into bounded implementation items before starting it. The version cannot close on an unbounded promise to support a format.

The [C function inventory](../api/current-c-api.md) lists every function in the current public headers and is checked for drift when Python is available. It does not certify contracts, examples, tests, types, or Lua parity. The [Lua namespace inventory](../api/lua-namespaces.md) records the namespace functions and links their guides; an automated check detects missing or extra namespace functions. The [process API baseline](../api/process-inventory.md) lists the contracts delivered in alpha.5. Use it when selecting the complete inventory and when adding new API names. The [input baseline](../api/input-inventory.md) maps the delivered C and Lua input APIs to contracts, examples, and tests; remaining input decisions are still open. The [audio baseline](../api/audio-inventory.md) records the delivered sound and music APIs and their verification limits.

## Execution plan

1. Establish the API inventory from the alpha.5 baseline and pinned references. Record a decision for every selected family and assign the remaining families to alpha.8.
2. Specify scroll, regions, and collision separately, including coordinates, lifetime, errors, C and Lua parity, and graphics or behavior tests. Implement each only after its contract is recorded.
3. Pin an FPG variant and licensed fixtures, then specify the Aseprite subset and rejection behavior. Implement each importer with fidelity and malformed-input tests.
4. Verify every delivered symbol and run the relevant C, headless, asset, and visual suites before closing the version. Manual device and user-flow checks remain in beta. Modes 7–9 and GUI remain outside 2.0.
