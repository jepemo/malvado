# 2.0.0-alpha.5: Process model and lifecycle

Status: planned. Complete the open alpha.3 and alpha.4 work in parallel with their existing gates. This alpha changes the experimental process APIs. The current contracts describe the implementation until this alpha is complete.

## Design and decisions

The target is one C scheduler with Lua namespaces and callable process definitions. `import_globals()` uses an atomic whitelist. Lua process properties include ordinary game fields and a small, validated set of system fields. Defaults are applied before spawn arguments and mutable defaults are independent. Spawn returns canonical userdata, also used as `self`. A dead handle retains only identity, status, and reason; other property access fails. Identity must distinguish contexts and prevent stale handle reuse.

A process ends on return or kill. Kill marks its targets dead immediately and defers physical cleanup to a safe point. Lua self-kill must stop the coroutine before its next instruction. Kill is idempotent on valid dead handles. Attached children end with their owner. Record the immutable creator separately from the owner. Creation defaults to attached inside a process; definition and instance policy can change future children, and explicit spawn options take priority. No implicit attach or detach is allowed.

`find`, `children`, and `descendants` return new, creation-ordered snapshots of live processes, including sleeping and frozen processes. Hierarchical queries default to ownership and may select creation. `kill_tree` follows creation history, including through dead ancestors; `signal_tree` defaults to creation and can select ownership. Validate collective operations before changing any target. Retain only the genealogy needed to connect live descendants to ancestors. A dead ancestor handle can be a creation-query root while its lineage remains; after pruning it has no live descendants.

Resources created by a process are owned by it by default; game-scope resources belong to the context. Shared use and pending renderer or audio work must retain independent references. Process ownership and resource ownership are separate. During cleanup, only explicitly independent spawns are allowed; runtime shutdown rejects all spawns. Do not add `on_exit`, `cancel`, `attach`, `detach`, or a general `query` API.

## Proposed namespaces and global names

This is a proposal for the 2.0 API inventory. The current flat API remains the implementation until migration. Keep one implementation per operation. Namespace entries and global aliases must call the same function and use the same arguments, results, and errors.

```lua
local mv = require("malvado")
local proc = mv.process
local input = mv.input

if input.key_down(input.KEY_UP) then
  proc.signal(enemy, proc.SIGNAL_KILL)
end

mv.import_globals()
if key_down(KEY_UP) then
  signal(enemy, SIGNAL_KILL)
end
```

- Define a reviewed export table that maps every public function and constant to one global name. Do not derive names from the set of collisions at runtime. Add new API entries to this table and check uniqueness in CI.
- Prefer a short, meaningful name when it is unambiguous and reserved by the published table, such as `frame` or `signal`. Use a stable domain prefix when needed, such as `sound_stop` and `video_stop`. These are naming examples, not a commitment to add video. Never rename an existing global automatically when a new module adds a function.
- Export the callable `process` namespace as `process`, so `process(fn)` and `mv.process(fn)` use the same mechanism. Map its explicit operations, such as `process.spawn`, to separately documented global names. Do not also export the import function itself. Every public operation must have one listed global alias; namespace tables do not need global aliases except the callable `process` table.
- Use uppercase domain-prefixed constants, for example `input.KEY_UP`, `input.KEY_A`, and `process.SIGNAL_KILL`, with globals `KEY_UP`, `KEY_A`, and `SIGNAL_KILL`. Propose stable string values such as `"up"`, `"a"`, and `"kill"`: they preserve readable calls and fit the current Lua string-based key and signal APIs. Accept the corresponding documented strings as well. Reject unknown values consistently. Constants from different domains are not interchangeable merely because their representation is a string; validate them at each API boundary.
- C keeps typed `MvKey` and `MvSignal` values and `MV_KEY_UP` and `MV_SIGNAL_KILL` names. Lua strings map explicitly to C values; their numeric representation is not shared. Document the mapping and test both APIs against the same behavior. Do not expose backend key codes as portable constants.
- Check the whole whitelist, including constants and callable tables, before changing globals. An existing equal value is allowed for repeat imports; a different value is a conflict. Use raw global table access for both validation and installation so metatables cannot cause partial imports or hide conflicts. Define behavior for a non-table global environment and allocation failure before implementation. Normal `require` must not install globals.
- Publish the complete mapping as the inventory grows. Check collisions with Lua standard globals, existing Malvado names, and between all planned domains. Treat a published alias change as an API change. Decide whether the existing legacy import remains a separately requested compatibility profile; do not merge it silently into the new import.

## Resolve before implementation

- [ ] Review and approve the complete namespace-to-global export table and constant families. Decide the remaining explicit names before implementation; reject duplicate or conflicting aliases in CI.
- [ ] Test all aliases, constants, string mappings, repeated imports, conflicts with standard and application globals, and atomic failure. Compare namespace and global behavior, and C/Lua key and signal behavior.
- [ ] Specify explicit Lua names and callable equivalence, reserved fields and validation, reason values, and spawn outside a running process. Resolve whether instance `children_attached` is a reserved field or a spawn option and prevent collisions with game data.
- [ ] Define defaults copying for cycles, shared references, metatables, functions, userdata, and native resources. Reject unsupported values explicitly. Define failure atomicity.
- [ ] Prototype Lua 5.4 self-kill and coroutine closing, including non-yieldable contexts and errors in `__close`. Verify that game code cannot catch termination and resume. Specify error reporting and cleanup continuation for natural return, self-kill, external kill, errors, and shutdown.
- [ ] Decide cleanup order for a snapshot of parents and children, reentrancy, and spawns from `__close`. Specify when handles become dead and when resources and genealogy are released. Prevent repeated destruction even when cleanup fails.
- [ ] Define resource acquisition, assignment, transfer, explicit release, and renderer/audio retention for each existing resource family. Audit fonts, text, textures, graphics and audio; preserve references held by existing objects. Define shutdown ordering and thread constraints.
- [ ] Define C types and signatures before changing the public header: context-scoped opaque identity with generation, spawn options for creator and owner, type identifiers for C and Lua, status and reason, idempotent kill, collective signal results, and snapshot ownership and allocation errors. Specify borrowed versus owned values, context lifetime, thread rules, invalid arguments, and no partial mutation on allocation failure. C callbacks cannot be interrupted like Lua: self-kill marks the process dead and the callback must return promptly; document and test this language difference.
- [ ] Design snapshot APIs without Lua callbacks during traversal. Specify stable ordering, dead-root tokens, filtering, capacity or allocation, and mutation rules. Evaluate creation adjacency, ownership adjacency, type indexes, pruning counters and iterative traversal; measure frequent queries, deep trees and long runs before selecting indexes.
- [ ] Decide the migration policy for numeric PIDs and the existing flat Lua API. Do not silently maintain a second API. Record breaking changes and provide a migration guide for C and Lua examples, tests, generated projects, inspector, and documentation.
- [ ] Specify inspector snapshots for both relationships, independent processes and retained dead ancestors without retaining process state or an unlimited history.

## Implementation and acceptance

- [ ] Implement identity and distinct creation/ownership relations in C, then canonical Lua handles and invalidation. Keep native state independent of Lua userdata lifetime.
- [ ] Implement safe termination and cleanup, resource references, ownership cascades, historical genealogy and incremental pruning. Use iterative traversal for deep trees. Snapshot signal targets before mutations.
- [ ] Implement queries and tree signals in C and Lua, including mixed C/Lua processes and historical roots. Update inspector and all affected contracts and examples.
- [ ] Add automated tests for natural termination, self-kill, killing a process before its turn, idempotence, dead handles, independent children, dead ancestors, both signal relations, query ordering, and invalid operations without partial effects.
- [ ] Test all Lua close paths, independent spawn during close, rejection of attached spawn during termination, shutdown spawn rejection, close errors, and exactly-once cleanup. Test shared resources and pending graphics/audio use without early release.
- [ ] Run mixed C/Lua parity, deep-tree and mass creation/destruction stress tests, long simulated games, complete genealogy pruning, and shutdown with no pending processes or resources. Include automated graphics checks for migrated resource behavior and memory instrumentation where supported.
- [ ] Update the alpha.6 API inventory and later implementation, platform, documentation and packaging work for the resulting contracts. Run automated emulator checks in the platform alpha. Manual user flows and physical-device checks remain in beta.

This is a target, not a claim that the implementation already has these behaviors. The open decisions above require explicit resolution before their dependent implementation is accepted.
