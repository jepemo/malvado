# 2.0.0-beta.1: candidate review and release preparation

Status: planned. Depends on alpha.7 and alpha.8 acceptance. Review the engine
already delivered; new API families, a complete example catalog, minigames and
a website redesign are not release gates. See the [future roadmap](../roadmap/README.md).

## Checklist

- [ ] Record the candidate's C/Lua/Rust API inventory, ownership, errors and platform limits. This is a release snapshot, not a permanent API freeze. Breaking changes within 2.x remain allowed until the owner explicitly changes the policy; document changes and migration requirements.
- [ ] Complete usable getting-started and reference documentation for delivered C, Lua and Rust capabilities, including scheduler, cancellation, resources and unsupported combinations. Link source contracts and tested commands.
- [ ] Provide a small aligned example set for startup, processes and a representative visual/resource flow, with common behavior, assets/licenses and bounded installed/exported tests. The full teaching catalog and minigames remain future work.
- [ ] Verify all claimed macOS, Linux, Windows and Android language/export paths, exact support matrix and continuous checks on the candidate revision. Keep missing automated behavior open rather than substituting manual plans.
- [ ] Manually test installation, project creation, examples, build/run/check/export, exported games, updates and removal on the supported authoring hosts.
- [ ] Manually test C/Lua/Rust games on clean supported desktop systems and Android devices. Record revision, platform, architecture and results for every claimed path.
- [ ] Manually check graphics, keyboard/mouse where applicable, physical controllers/hotplug, audible sound/music and mobile background/foreground behavior. Distinguish unsupported capabilities from untested claims.
- [ ] Resolve release-blocking issues and rerun affected automated/manual checks on the revised candidate.
- [ ] Review dependencies, licenses, notices, package contents and checksums; verify that players do not need authoring toolchains.
- [ ] Publish or prepare versioned documentation for the candidate using the existing site workflow. Preserve current URLs; a new site framework is not required.
- [ ] Prepare tested release candidates and draft artifacts with their exact source revision, support matrix, checksums, known limits and release notes. Tagging, publication and production signing require explicit authorization.
